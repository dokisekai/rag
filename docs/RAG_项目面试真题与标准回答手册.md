# 🎯 RAG 项目面试真题与满分回答手册 (Interview Q&A Guide)

本文档整理了在模拟面试过程中涉及的**所有核心问题、候选人回答要点、面试官点评、技术原理解析以及满分标准回答模板**。旨在帮助你将项目中的硬核工程细节转化为面试时最能打动面试官的话术。

---

## 📌 第一轮：项目总体架构与业务场景

### ❓ 问题 1：请简要介绍一下你的这个 RAG 知识库项目，它的业务场景和核心数据链路是怎样的？

* **业务痛点**：解决电商商城客服咨询量大、人工客服成本高昂的问题，通过 AI 知识库实现自动解答，达到**降本增效**的目的。
* **数据链路**：文档上传 ➔ 段落结构化切块 ➔ Embedding 向量化落盘 ➔ 关键词+向量混合检索 ➔ LLM 上下文整合与回答生成 ➔ Chunk 来源追溯。

#### 💡 满分标准回答模板：
> “面试官你好！我负责的这个 RAG 知识库项目主要应用于**电商商城智能客服场景**。电商系统用户咨询量大、重复性问题多，人工客服是一笔很大的运营支出。项目的核心目标就是通过私有知识库问答来实现自动化解答，降低客服成本。
> 
> 在架构设计上，系统的核心数据链路分为两部分：
> 1. **数据构建链路**：支持 PDF/Word/PPT 多格式文档解析，采用滑动窗口重叠切块，提取 Embedding 向量后落盘到 FAISS 向量数据库中，同时生成元数据映射。
> 2. **问答检索链路**：用户提问先经过数据护栏脱敏，随后触发 **FAISS 向量检索与 BM25 字面检索** 的并行混合检索，使用 **RRF 算法** 融合重排并进行相似度阈值截断，最后拼接 System Prompt 送入 LLM 流式输出回答，并保留 Chunk 出处供溯源。”

## 📌 第二轮：RAG 核心技术细节挖掘

### ❓ 问题 2：在电商场景下，退换货政策或商品参数常遇到段落被切断的问题，系统如何解决上下文断裂？

#### 💡 满分标准回答模板：
> “我们在文档解析层实现了 **滑动窗口重叠切块（Sliding Window Chunking）** 机制。默认设置 Chunk Size 为 500 字符，同时保留 **100 字符的 Overlap（重叠区）**。即使一段核心规则刚好跨越切片边界，重叠区也能保证该规则在至少一个 Chunk 中保持语义完整。
> 针对表格数据（如规格参数表），解析器会自动将其提取为 Markdown 格式（`| 列A | 列B |`）并保持独立节点，尽量避免表格行被中途切断。”

---

### ❓ 问题 3：向量检索分数值与 BM25 分数值量级不同，系统是如何进行融合打分的？

#### 💡 满分标准回答模板：
> “我们在后端采用了 **RRF (Reciprocal Rank Fusion，倒数排名融合算法)**。
> 因为向量余弦相似度（0~1）和 BM25 得分（0~几十）的分值范围完全不同，直接加权求和极易失真。RRF 算法只关注文档在各自列表中的相对排名，打分公式为：
> $$S(d) = \sum_{m \in \{Vector, BM25\}} \frac{w_m}{k + rank_m(d)}$$
> 其中 $k$ 取 60。这样既保留了向量检索的语义泛化能力，又结合了 BM25 对商品型号、代码类名的精准匹配，免去了复杂的得分归一化。”

---

### ❓ 问题 4：如何保证回答绝对真实？万一知识库查不到资料怎么办？

* **亮眼工程思路**：**阈值截断 + 友好提示转人工（Human-in-the-loop）**。

#### 💡 满分标准回答模板：
> “我们在系统设计了双重保障：
> 1. **严格知识库模式 (Strict KB Mode)**：在 System Prompt 中强约束‘绝对不使用先验知识，资料中未提及则明确告知未找到’；同时设定 Similarity Threshold 相似度得分截断。
> 2. **转人工降级策略 (Human-in-the-loop)**：当系统判定检索到的 Chunk 得分低于阈值时，不强行让 AI 瞎编，而是向用户输出友好提示，并自动将会话路由转接给人工客服介入处理，保障电商业务绝对不出错。”

---

## 📌 第三轮：LLM 控制、反向代理与容灾降级

### ❓ 问题 5：私有化部署开源小模型（如 7B/14B）通常不支持原生 Tool Calling，怎么解决？

#### 💡 满分标准回答模板：
> “我们在 FastAPI 后端设计了 **/api/llm-proxy 工具调用代理层**：
> - **请求拦截**：检测到请求中带有 `tools` 参数时，自动在最后一个 User 消息尾部注入强约束的 JSON Schema 格式说明与 Few-Shot 示例，诱导开源模型输出标准 JSON。
> - **响应补全 (Synthetic Tool Call Wrapping)**：若开源模型仍返回纯文本或残缺结构，代理层会捕获响应并启动包装引擎，自动构造符合 OpenAI 规范的 `tool_calls` JSON 返回，对上层 Agent 业务完全透明。”

---

### ❓ 问题 6：当流式输出（SSE）中断或本地大模型挂掉时，有什么容灾降级机制？

* **亮眼工程思路**：**上下文记忆 + 云端 API Failover 自动续写**。

#### 💡 满分标准回答模板：
> “我们设计了 **云端 API 容灾续写降级机制 (Cloud Failover & Completion)**：
> 当检测到本地 LLM 响应超时、服务崩塌或 SSE 连接异常中断（只生成了半截回答）时，系统会捕获中断事件，保留近几轮对话上下文以及已生成的半截文本，自动无缝 Failover 切换至云端 API（如 DeepSeek / Qwen API），让云端模型接替失败内容继续流式续写，保障用户无感知且体验不中断。”

---

## 📌 第四轮：前沿协议扩展 (MCP 与 Skills)

### ❓ 问题 7：什么是 MCP (Model Context Protocol) 协议？如何解决查订单等动态数据需求？

#### 💡 满分标准回答模板：
> “**MCP (Model Context Protocol)** 是 Anthropic 提出的下一代大模型上下文与工具交互的标准通信协议（类似 LSP 语言服务协议）。
> 针对‘查订单’、‘改地址’等动态需求，静态 RAG 是查不到的。我们通过系统内置的 **SkillsService** 和 **MCPClient**：
> 1. 将查询订单接口定义为标准 Skill 插件或 MCP Tool（暴露入参 Schema）。
> 2. 大模型识别到用户意图后触发 Tool Call，通过 JSON-RPC 2.0 调取后端的 `script.py` 或外部 MCP Server 实时拉取数据库中的最新订单状态，最后由 LLM 汇总生成解答。”
